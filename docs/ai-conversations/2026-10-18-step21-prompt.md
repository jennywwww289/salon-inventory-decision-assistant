# 步驟二十一｜第一輪：排版

## 一、主要目標
### 動作
依步驟20的研究結果，改善留白、區塊排列及響應式配置，優先修正：
1. 窄版固定側欄占用主要內容寬度。
2. 頂部工具列、搜尋與篩選擁擠。
3. 表格欄位過窄、內容或操作入口被裁切。

### 目的
讓桌機、平板與手機皆能閱讀主要內容並操作既有功能，完成第一輪獨立美化。

## 二、輸入
### 動作
讀取：
- docs/design-principles-research.md，或實際同用途研究文件。
- docs/initial-self-evaluation.md。
- docs/screenshots/before/README.md及相關初版截圖。
- 實際控制首頁、系統外框、側欄、頂部工具列、庫存表格與彈窗的元件及樣式。

先確認現有程式與未提交變更，再決定最小修改範圍。
記錄本輪開始時的版本識別，保留其他既有修改。

### 目的
以目前專案和可確認的問題為準，不依過去要求假設程式已完成。

## 三、本輪範圍
### 動作
只處理排版：
- 容器寬度、留白、間距、排列、換行。
- 響應式側欄與工具列。
- 表格捲動與彈窗尺寸。
- 手機導覽正常操作所必要的狀態與鍵盤處理。

優先沿用既有Tailwind、CSS及元件，不新增UI框架或重寫網站。
首頁若沒有明確排版問題，可保持現狀。

### 範圍限制
- 文字層級留到步驟22；裝飾性動畫與互動樣式統一留到步驟23。
- 保留個人資料、公開Email、文案與示範標示。
- 保留庫存、交易、採購、驗證、統計及LocalStorage規則。
- 不修改原始截圖，不移動original-baseline與pre-beautification-v1標籤。
- 不讀取或輸出憑證內容。

## 四、任務
### 任務1：修正共用版型與窄版導覽
動作：
- 寬螢幕保留合理的側欄與內容配置。
- 寬度不足時，採符合現有結構的可收合導覽或抽屜，讓主要內容取得可用寬度。
- 導覽開關使用真正button，提供可辨識名稱及aria-expanded等必要狀態。
- 選單全部可捲動到達，切換分頁後合理收合，返回個人首頁正常。
- 若採遮罩式抽屜，處理關閉按鈕、Esc、焦點進出及必要的焦點限制。
- 不因返回首頁再進入系統而重新建立Provider或重設資料。
- 主要觸控目標至少44×44 CSS px，作為本專案規格。

目的：
避免側欄擠壓內容，同時保留原有分頁與操作入口。

### 任務2：整理工具列、搜尋與區塊間距
動作：
- 依內容需求使用Grid或Flexbox，調整換行、間距與欄數。
- 搜尋欄、篩選器及主要按鈕在窄版可換列，避免彼此覆蓋。
- 保留原有搜尋、篩選及清除條件的事件與功能。
- 檢查共用版型變更影響的其他分頁，只修正同類排版問題。
- 頁面標題、內容區及卡片使用少量一致的間距規則。

目的：
讓內容順序清楚，避免透過縮小整頁或隱藏功能勉強容納。

### 任務3：修正表格與彈窗
動作：
- 表格維持語意及可讀欄寬，需要時在表格自己的容器內橫向捲動。
- 搜尋、標題與分頁控制仍應隨畫面重排。
- 操作欄及重要數據必須可以到達，不以全頁overflow-hidden掩蓋裁切。
- 彈窗寬度不超出視窗，短螢幕下內容可捲動，關閉與提交按鈕可到達。
- 優先修正共用彈窗配置，避免逐個複製不同規則。

目的：
保留表格資訊與表單操作，改善窄版及低高度畫面的可用性。

### 任務4：留下第一輪修改證據
動作：
- 保存本輪完整Prompt，沿用既有對話紀錄方式。
- 記錄「問題→研究原則→修改位置→修改原因→驗收結果」。
- 截圖存入docs/screenshots/round-1-layout/，附簡短README。
- 至少保留庫存清單桌機、平板、手機各一張修改後截圖。
- 首頁或彈窗若有修改，再補能證明變更的代表畫面，避免重拍無關頁面。
- 對照初版使用相同資料來源、頁面狀態與拍攝條件：
  桌機1440×900、平板820×1180、手機390×844。
- 同時記錄設定的viewport與實際圖片尺寸，保留既有尺寸差異紀錄。
- 測試與截圖使用獨立環境，不重設日常瀏覽器已保存的資料。
- 更新開發紀錄，保存本輪版本識別及修改檔案清單。

目的：
讓第一輪排版修改具有可追溯的前後比較證據。

## 五、輸出
### 動作
交付：
1. 本輪排版相關程式與樣式修改。
2. 第一輪修改紀錄、完整Prompt及可取得的前後比較證據。
3. 測試結果與尚待驗證項目。

若建立Git提交，只納入本輪可確認的修改，不混入其他既有工作。

## 六、驗收與回報
### 程式檢查
- npm run lint及npm run build各執行一次。
- 沿用現有核心回歸測試，跑一輪即可。
- 不新增只檢查CSS類別名稱或鏡像實作的測試。
- 有失敗先釐清是否由本輪引入，不順便擴大重構。

### 畫面與操作檢查
瀏覽器工具可用時，優先自動完成：
1. 首頁與庫存清單在三種尺寸下的排版檢查。
2. 手機導覽開啟、切換分頁、關閉及返回首頁。
3. 搜尋／篩選及清除條件的代表操作。
4. 開啟一個主要表單彈窗，檢查窄版與短高度下按鈕可到達；不需提交新增資料。
5. 檢查頁面溢位、主要觸控目標尺寸與本輪新增的Console錯誤。

沿用現有工具；若瀏覽器工具仍不可用，不重複嘗試或安裝大型測試框架。
先完成可執行的程式檢查與紀錄，畫面、點擊及截圖標示待補。
最後只提供一次精簡的必要人工補證流程與截圖清單，不要求重做步驟17全部功能測試。
人工步驟使用「點哪裡／輸入什麼／預期看見什麼」。

### 回報格式
使用表格列出：
測試目的／測試輸入／預期輸出／實際輸出／問題與通過判定。

另外精簡列出：
- 修改檔案、主要變更及原因。
- 三尺寸排版、手機導覽、表格與彈窗的驗證結果。
- 前後截圖與版本位置。
- 既有警告、本輪新增問題及未驗證項目。

區分「程式已實作」「靜態或mock測試通過」「真實瀏覽器已驗證」。
未完成的畫面驗收不能用build或mock結果代替。

完成後停止於步驟21，不進入步驟22。
