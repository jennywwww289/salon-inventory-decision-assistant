# 步驟二十三｜第三輪：互動回饋

## 一、主要目標
### 動作
整理主要操作的hover、鍵盤焦點、按下、停用、成功、錯誤及真實等待狀態，加入適度transition。
### 目的
讓使用者清楚知道哪些元件可以操作、操作是否完成，以及失敗時如何處理，完成第三輪獨立美化。

## 二、輸入
### 動作
讀取：
- 步驟20研究文件中的微互動、按鈕狀態、狀態訊息及減少動態效果原則。
- 步驟21、22的最終修改與驗收紀錄。
- 第二輪截圖清單與有效圖片。
- 首頁複製Email、共用按鈕、表單、搜尋篩選、手機導覽及訊息回饋的實際程式。
- 相關既有測試與package.json。

### 目的
沿用已完成的排版與文字層級，只補足現有互動回饋缺口。

## 三、本輪範圍
### 動作
優先處理共用樣式及代表性操作：
1. 首頁主要入口與複製Email。
2. 系統主要按鈕、搜尋篩選及表單。
3. 手機導覽與既有成功／錯誤訊息。

先盤點現有功能；已完整的部分沿用，避免重寫。

### 限制
- 保留第一、二輪的排版與文字規格。
- 不改動庫存、交易、採購、驗證、統計及保存規則。
- 保留AI、角色及LINE／Email通知的示範定位。
- 不新增人工等待、假載入、假成功或真實寄送服務。
- 不新增動畫套件或UI框架。
- 保留既有修改、原始截圖與兩個基準標籤。
- 不讀取或輸出憑證內容。
- 使用者已決定跳過步驟24，不擴大進行整站配色、圓角、邊框或陰影改版。

## 四、任務
### 任務1：記錄起點與互動缺口
動作：
- 記錄本輪開始版本及既有未提交變更。
- 簡列「元件／已有狀態／缺少回饋／本輪處理方式」。
- 瀏覽器工具可用時，修改前先保存一組代表性狀態畫面。
- 工具不可用則保存版本與程式位置，截圖標示待補，不要求使用者重拍。

目的：
讓第三輪修改有明確依據，避免為了增加效果而改動全部元件。

### 任務2：統一可操作元件的狀態
動作：
- 主要按鈕及連結具有可辨識的hover與按下回饋。
- 鍵盤操作有清楚的focus-visible，不能只靠hover辨識位置。
- 觸控操作不依賴hover才能看到功能。
- 停用狀態外觀清楚，必要時說明不可操作的原因。
- 停用必須有實際行為限制，不能只降低透明度。
- 沿用正確的button、a及原有事件；避免為樣式重綁事件。
- 保留主要觸控區域，不因狀態樣式縮小。
- 使用既有色系與共用方式，避免廣泛全域規則誤傷其他元件。

目的：
讓滑鼠、鍵盤與觸控使用者都能辨認操作狀態。

### 任務3：校正成功、錯誤及等待回饋
動作：
- 成功訊息依實際動作結果顯示，不在點擊時預先宣告成功。
- 失敗沿用具體原因，保留輸入，不錯誤關閉表單或清空內容。
- 訊息使用清楚文字，不能只依賴顏色。
- 沿用或補足適當的role=status、aria-live等訊息語意，避免重複播報。
- 確認既有保存失敗警告與示範說明沒有被短暫提示覆蓋。

複製Email：
- 沿用現有實作，不重寫已正常工作的工具函式。
- 真正等待Clipboard Promise時才顯示等待狀態並防止重複觸發。
- 寫入成功後才顯示成功。
- 拒絕或不支援時顯示失敗與手動複製說明。
- 不讀取使用者剪貼簿內容。

同步操作：
- 搜尋、篩選及同步資料操作不增加假spinner或人工延遲。
- 原有防重複驗收、失敗阻擋及交易規則維持有效。

目的：
讓回饋與實際結果一致，避免視覺效果誤導使用者。

### 任務4：加入適度動態效果
動作：
- transition限於需要變化的屬性，避免全面使用transition-all。
- 可從約120～200ms開始，作為本專案選擇，依實際效果調整。
- 避免造成版面跳動、文字模糊或干擾操作的效果。
- 遵守prefers-reduced-motion，減少或取消非必要動畫與平滑捲動。
- 減少動態效果時，焦點、成功與錯誤回饋仍須立即可辨。

目的：
讓操作銜接自然，並尊重使用者的動態效果偏好。

### 任務5：保存第三輪證據
動作：
- 保存完整Prompt、修改檔案、原因與版本。
- 證據存入docs/screenshots/round-3-feedback/，附README。
- 工具可用時，至少保存一組同元件、同畫面條件及同狀態的修改前後截圖。
- 成功／錯誤等操作回饋，工具可用時再保存最少量的代表證據。
- 靜態截圖不當作動畫流暢度或真實操作成功的證明。
- 無法取得的圖片或操作證據如實標示待補。
- 第二輪既有截圖、Console及44px量測缺口沿用紀錄，有新證據才更新。
- 開發紀錄註明「步驟24依使用者指示跳過」。

目的：
保留第三輪的作業證據，同時控制額外操作時間。

## 六、驗收與回報
### 自動檢查
- npm run lint及npm run build各執行一次。
- 若改動複製Email事件，執行相關既有測試，涵蓋等待、成功、拒絕及不支援。
- 其他事件若有改動，只執行受影響的既有測試，必要時補少量有意義的行為測試。
- 純樣式變更不新增只比對CSS類別或鏡像實作的測試。
- 不為展示本輪成果而新增大量測試。

### 瀏覽器工具可用時
自動檢查代表性操作：
- Tab焦點可見、Enter／Space操作符合元件行為。
- 停用狀態不能觸發原動作。
- 複製Email及一個表單的成功／失敗回饋正確。
- 手機導覽既有開關、Esc及收合行為沒有退步。
- 減少動態效果設定生效。
- 檢查本輪新增的Console錯誤。

使用獨立測試環境，不改動日常已保存資料；Clipboard等環境能力可用受控mock驗證，但要明確標示。

### 真人測試安排
本輪不安排例行真人測試，也不要求使用者逐項點擊、錄影或重拍截圖。
若瀏覽器工具不可用：
- 不反覆嘗試相同失敗方式，不安裝大型框架。
- 完成可執行的程式檢查與相關測試。
- 將真實瀏覽器、動畫流暢度及截圖缺口集中列入紀錄。
- 不以「等待使用者補拍」作為本輪工作的停止點。
- 最終必要的本人驗收留到後續階段再集中處理。
